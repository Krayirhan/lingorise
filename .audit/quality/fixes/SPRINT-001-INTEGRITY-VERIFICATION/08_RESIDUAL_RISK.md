# SPRINT-001 — Residual Risk

| Risk | Related Global finding | Why unresolved | Actual impact | Why safe/unsafe to defer | Required future owner |
|---|---|---|---|---|---|
| Firestore emulator rules tests (`npm run test:rules`) could not be executed locally | GLOBAL-QA-014, GLOBAL-QA-031 | Pre-existing environment gap: `firebase-tools` requires JDK 21+, only JDK 17 is installed on this machine (also blocked the original baseline audit) | The new `firestore.rules` validation and the new `dailyTasks` cross-user test are E2 static-verified (careful reading, consistent with the existing already-passing test pattern) but not E3 executable-verified this pass | Safe to defer to a machine/CI runner with JDK 21+ — no code change can fix a local JDK version; do NOT weaken the verification requirement to work around it | Targeted VERIFICATION-ASSURANCE reaudit, or a CI run on a compatible runner, before this closure is treated as fully E3-verified |
| `normalizeUserData()`'s own field list (`src/services/storage.ts`, untouched this sprint) is a separate, non-compiler-enforced manual list | MAINT-QA-001 (partially) | Out of this sprint's mandate — Sprint 1 owns the *merge* layer's canonical schema, not the *local-storage normalization* layer's | A new optional `UserData` field could still be silently dropped during the local AsyncStorage round trip (a different, narrower defect shape than DATA-QA-002, which was specifically about the cloud merge) — bounded to local persistence, not cross-device data loss | Safe to defer — no evidence this has ever caused a real defect (unlike the merge layer, which had a proven one); flagged here so it isn't forgotten, not because it's urgent | A future targeted Maintainability recheck, if `storage.ts` is touched again for another reason, or a dedicated small follow-up |
| `syncUserProgress()` still writes a manually-curated field subset (`xp`, `level`, `streak`, `lastActiveDate`, `practiceHistory`) to the lightweight `progress/main` doc, not the full canonical set | CODE-QA-003 (partially) | This is an intentional, pre-existing design (a lightweight progress-summary document, not a full mirror) — Sprint 1 did not change its scope, only fixed the *merge* function that reads both `users/{uid}` and normalizes the result | None currently — `users/{uid}` (written by `syncUserData`) remains the full-fidelity source the merge reads from; `progress/main` is a deliberately smaller summary | Safe to defer — this is a documented design choice (a summary doc), not a silent omission; revisit only if `progress/main` is ever expected to be a full mirror | Owner: whoever next touches `syncUserProgress`'s scope intentionally: not a Sprint 1/2/3 blocker |
| Account deletion cannot be made truly cross-service-atomic | GLOBAL-QA-007 (DATA-QA-004 / SEC-QA-003) | The client-only architecture has no distributed-transaction mechanism spanning Firestore and Firebase Auth | A `PartialAccountDeletionError` window can exist between "Firestore data deleted" and "Auth credential removed" if the second call fails (e.g. `auth/requires-recent-login`) — bounded and self-healing on retry (`deleteUserData` is idempotent on already-empty collections/docs), but not instantaneous | Safe to defer — implementing true atomicity would require a backend Cloud Function/transaction architecture, explicitly out of proportion for this sprint's mandate ("do NOT invent a materially larger backend architecture") | Documented, bounded limitation; would only become a required fix if evidence emerges that users are getting stuck in the partial state without retrying |
| `RemoteStateUnknownError`'s actual trigger (a live Firestore read failing over the network) is not exercised end-to-end by an executable test | GLOBAL-QA-003 | Requires a live or mocked Firestore SDK; the project's `ts-node` test runner has neither, and building one was judged disproportionate ("do not add a giant mocking framework solely for these tests") | Low — the *decision* consuming that failure (`decideMergeAction`) is now fully unit-tested (post-review fix); only the underlying network-call wiring itself (which is a direct, short, unchanged-pattern `try/catch` around `getDoc`, consistent with every other Firestore read in this file) is unverified | Safe to defer — the same limitation already existed for every other Firestore call in this codebase before this sprint; this sprint did not introduce a new gap, it made the previously entirely-untested decision logic testable | No dedicated owner needed unless a future E2E/emulator-based test harness is introduced project-wide |

No severity was downgraded by this sprint. Only a later targeted reaudit may formally rescore or reclassify any of the findings above.
