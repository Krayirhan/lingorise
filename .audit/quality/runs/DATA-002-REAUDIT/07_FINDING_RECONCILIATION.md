## New findings discovered during this reaudit

Two of the three findings below were refined or discovered through an independent `code-reviewer` challenge pass run against this reaudit's own draft (see `09_INDEPENDENT_REVIEW.md`) — its ADJUST verdict is incorporated directly here rather than left as a separate unreconciled opinion.

### DATA-QA-006 (NEW) — a long-stale local `streak` can be silently, persistently resurrected past a genuine account-wide reset

**Severity: P2** (upgraded from this reaudit's own initial P3-equivalent oversight after independent challenge — see rationale below).

**Root cause, independently re-verified against the actual call chain:** `src/app/AppBootstrap.tsx`'s `onAuthStateChanged` handler calls `mergeAndSyncUserData(uid, localData)` where `localData = await loadUserData()` — and `loadUserData()` (`src/services/storage.ts`) performs ONLY schema migration/normalization, never streak-rollover math. So the `streak` value entering the merge can be a stale number from the last time this specific device was actually opened, not a value that reflects any gap since then. `mergeUserData`'s `streak: Math.max(local.streak, remote.streak)` then treats that stale number at face value: if a signed-in user hasn't opened this specific device in, say, 5 days (local streak frozen at, e.g., 30) while genuinely maintaining a lower, correctly-decayed streak on another device (remote streak, e.g., 5, correctly reset via that other device's own `updateDailyStreak` calls), the merge resolves to `max(30, 5) = 30` and persists it as canonical to both local and Firestore.

**Why this is sticky, not self-correcting:** `updateDailyStreak()` (`src/domain/gamification/streak.ts`) determines whether a gap occurred by comparing `lastActiveDate` to today — NOT by validating the `currentStreak` number against that gap. Because the same merge also sets `lastActiveDate` to the later (today's) date via the `LATER_DATE_STRING` strategy, `refresh()`'s subsequent `updateDailyStreak(lastActiveDate="today", streak=30)` call sees `lastActiveDate === todayFormatted` and returns `Math.max(1, 30) = 30` unchanged — no gap is detected, because the date half of the pair (correctly "today") no longer carries any information about the actual gap the streak half (30) should have been reset for. The inflated value then continues incrementing normally on subsequent real days, indistinguishable from a legitimate streak, until the next sufficiently long gap happens to reset it independently.

**Why P2, not lower:** reproducible under ordinary (not exotic) multi-device or multi-session use; the two merged sub-values (`streak`, `lastActiveDate`) are computed independently from potentially different "sides," and their combination is what breaks — a genuine "meaningful reproducible integrity defect" per this rubric's own P2 definition. Not P1: it inflates rather than destroys progress, corrupts no other field, and is bounded to a single gamification counter (not the user's actual learning data/progress record).

**Test-fidelity gap directly responsible for this passing undetected:** `tests/testSuite.ts`'s two-device cold-start test (§56) computes `localRolloverState` by applying `updateDailyStreak`/`applyDailyRollover` to the local side BEFORE calling `mergeUserData` (lines ~1599-1607) — this does NOT match `AppBootstrap`'s actual production sequence, which merges the RAW, non-rolled-over `loadUserData()` output. The test's own comment ("This IS the call `mergeAndSyncUserData()` makes in production") is therefore not accurate for this specific pre-processing step, independently confirmed by re-reading both the test and `AppBootstrap.tsx` side by side. This is not a fabricated test (it does call the real `mergeUserData` function, correctly, for everything after that pre-processing step) — but the pre-processing gap is exactly why this scenario was not caught by Sprint 1's otherwise-extensive test matrix.

**Directly discovered in Sprint-1-touched Data paths:** Yes — `streak`'s `MONOTONIC_MAX_NUMBER` merge line is Sprint-1-touched code (now living in `mergeUserData`), and this reaudit's own test-fidelity trace is what surfaced the gap between the test's setup and the real call site.

**Recommended remediation (not performed by this reaudit):** route `streak` through the same day-scoped treatment already built for `dailyQuests`/`dailyReviewXpIds` — validate that the higher side's `streak` is only trusted when its own `lastActiveDate` is itself recent enough (e.g. within 1 day of "today") to plausibly support that streak count, falling back to a fresh `updateDailyStreak` recomputation otherwise; or normalize/roll-over `localData` before it enters `mergeAndSyncUserData` in `AppBootstrap.tsx`, so the merge always receives an already-gap-corrected streak.

### DATA-QA-005 (NEW) — `level`'s HIGHER_LEVEL merge strategy can override an intentional manual downgrade

**Severity: P2** (upgraded from this reaudit's initial P3 assessment after independent challenge — see reachability correction below).

**Root cause:** `level` was classified as `HIGHER_LEVEL` (an achievement-style field that should only ever advance), matching `xp`/`passedLevelExams`'s treatment. However, `level` also serves a second, distinct product role: a free, user-reversible content-selection preference, directly settable downward via `LevelSwitcherModal` ("Every level is selectable... never locked") → `setLevel()` (wired in `src/app/AppNavigator.tsx`). A merge shortly after an intentional downgrade — before the change has propagated — can silently restore the higher, now-stale value.

**Reachability correction (why P2, not P3):** this reaudit's own initial assessment underestimated reachability by framing it as requiring "multi-device" use. Independently re-verified: Firebase's `onAuthStateChanged` (the merge's trigger) fires on every app cold start for any previously-signed-in user whose session persists locally (this app configures `initializeAuth` with `AsyncStorage` persistence in `src/services/firebase.ts`) — not only on first sign-in. So the reachable trigger is: (1) intentionally switch to a lower level, (2) the resulting `updateAndPersist`'s background cloud sync has not yet completed (any transient delay, or simply closing the app quickly), (3) the app is cold-started again (a single device is sufficient — no second device required). This matches the same "ordinary, default-experience reachability" bar the original DATA-QA-002 P1 finding was held to, warranting P2 here (bounded to content-selection with a simple recovery, so not P1, but clearly more reachable than an exotic multi-device edge case).

**Evidence level:** E2 (direct source read: `LevelSwitcherModal.tsx`'s existence/copy and wiring, `progressMerge.ts`'s `higherLevel()` function, `firebase.ts`'s persisted-auth configuration). Not independently reproduced at runtime this pass.

**Directly discovered in Sprint-1-touched Data paths:** Yes — `level`'s merge strategy is new code introduced by this sprint.

**Recommended remediation (not performed by this reaudit):** either (a) treat `level` as `REMOTE_AUTHORITATIVE`/latest-write-wins if a per-field last-modified timestamp is introduced, or (b) keep `HIGHER_LEVEL` only as a floor derived from `passedLevelExams` (never merge below the highest level a passed exam has actually unlocked), otherwise respecting the more-recently-set value above that floor.

## normalizeUserData() residual — final disposition (refined after independent challenge)

**NOT a distinct new Data Integrity finding, but the independent reviewer identified a real, more concrete instance than this reaudit's own initial pass had characterized.** `fillDefaults()` (`src/services/storage.ts:265-291`) validates most array-typed fields with `Array.isArray(...)`, but `dailyQuests` (line 282: `(parsed.dailyQuests as UserData["dailyQuests"]) || DEFAULT_USER_DATA.dailyQuests`) and `learningProgress` (line 284: `(parsed.learningProgress as Record<string, LearningItemProgress>) || {}`) use only a truthy check, not a real shape/array-type guard — independently confirmed by direct reading. A malformed (wrong-type but truthy) stored value for either field would pass through uncorrected and could throw at a downstream call site (e.g. `mergeDailyQuestsSameDay`'s `.find()`, or `mergeLearningProgress`'s `Object.entries()`). This is pre-existing (unmodified by Sprint 1) and remains maintainability-tier, not a proven current defect (no evidence any stored value is actually malformed in this way in practice) — but it is a slightly more concrete gap than "narrow, low-materiality" alone conveyed, and is reflected as a small deduction in the Schema migration & normalization dimension (see `08_SCORECARD.md`).

## Firestore rules validation — Data relevance check

`isValidUserDoc()`'s new validation (`firestore.rules`) was checked against every current legitimate production write to `users/{userId}` and `users/{userId}/progress/main`: `syncUserData()`'s full-object mirror and `syncUserProgress()`'s curated subset both always write `xp`/`streak` as non-negative numbers (guaranteed by `Math.max(x, 0-or-more)` in the merge, and `0` as the schema default), `level` as one of the six valid `LevelCode` values (guaranteed by `higherLevel()`'s domain), and `passedLevelExams`/`unlockedBadges`/`solvedQuestionIds`/`rewardedQuestionIds`/`celebratedLevels` as arrays (guaranteed by `unionValues()`'s `Array.from(...)` return type). No legitimate current write path can be rejected by this validation — independently confirmed by tracing every value's origin back through the merge/default logic, not merely by reading the validation function in isolation. This validation could not be executed against a live emulator this pass (see `06_TEST_AND_RUNTIME_EVIDENCE.md`), but poses no Data-integrity risk to legitimate writes based on this static trace.
