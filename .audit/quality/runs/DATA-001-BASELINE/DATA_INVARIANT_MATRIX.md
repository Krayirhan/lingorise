# DATA-001-BASELINE — Data Invariant Matrix

Revision: 16b9aab

| Invariant | Owner | Evidence | Status |
|---|---|---|---|
| Successful local progress must survive ordinary app restart | `services/storage.ts: loadUserData/saveUserData` | E2 (AsyncStorage read/write, defensive `normalizeUserData`/`fillDefaults`) + E4 (repeated real-device restarts this session) | PASS |
| A failed cloud sync must not erase valid local progress | `state/useUserProgress.ts: updateAndPersist` (local `saveUserData` fires independently of the cloud `Promise.all(...).catch()`) | E2 | PASS (for the single-mutation case — local write is never gated on cloud success) |
| **A failed *remote fetch* during merge must not be treated as "no remote data exists"** | `services/firestore.ts: fetchUserData` / `mergeAndSyncUserData` | E2 (both `!snap.exists()` and a caught fetch error return the same `null`) | **FAIL** (DATA-QA-001) |
| **Login/cold-start merge must not silently regress a field the learner has legitimately advanced locally** | `services/firestore.ts: mergeAndSyncUserData` | E2 (`passedLevelExams`, `dailyQuests`, `questHistory`, `celebratedLevels`, `practiceHistory`, `dailyReviewXpIds`, `level`, `lastActiveDate` are not in the explicit re-merge list and are taken wholesale from `...remote`) | **FAIL** (DATA-QA-002) |
| Repeated synchronization should be idempotent where intended | `syncUserData`/`syncUserProgress` (`setDoc(..., {merge:true})`, whole-object writes) | E2 — re-running a sync with the same data is a no-op; re-running `mergeAndSyncUserData` is *not* idempotent for the fields in DATA-QA-002 (each run can re-apply the regression) | PARTIAL |
| The same logical reward/progress record should not multiply unexpectedly | `domain/practice/answer.ts` (`isFirstEncounter` gate), `domain/learning/mastery.ts: mergeLearningProgress` (whole-record, never spliced) | E2 + E3 (testSuite.ts) | PASS |
| Schema migration should preserve recognized historical progress | `services/storage.ts: migrateV1ToV2/migrateV2ToV3` (shape-detecting, self-healing, run unconditionally) | E2, well-commented rationale, no concrete defect found | PASS (minor theoretical confidence gap — see Known Limitations) |
| Corrupted/malformed optional fields should not destroy otherwise recoverable data | `services/storage.ts: fillDefaults` (per-field `Array.isArray`/type guards) | E2 | PASS |
| A `JSON.parse` failure on the whole stored blob falls back safely (no crash) | `loadUserData`'s outer try/catch → `DEFAULT_USER_DATA` | E2 — safe, but the fallback also discards data if *migration itself* throws, not just on parse failure (broad catch scope) | PARTIAL (E1 hardening note, no concrete trigger found) |
| Guest progress behaves according to the current product promise ("guest mode works fully without an account") | `app/AppBootstrap.tsx` (8s `onAuthStateChanged` timeout → guest fallback) | E2 + E4 (repeated this session) | PASS |
| Cloud merge must not invent stronger learning state than either legitimate source allows | `mergeLearningProgress`/`pickRicherRecord` (attempts count, then server timestamp, then device clock — whole record taken atomically) | E2, well-reasoned, E3 (testSuite.ts multiple scenarios) | PASS |
| **A "local data reset" that promises irreversibility must actually be irreversible for the user who triggered it** | `features/profile/components/DataManagementCard.tsx` + `services/storage.ts: clearAllLocalData` | E2 (reset button/copy identical regardless of `isCloudSynced`; `clearAllLocalData` never touches Firestore; next auth-triggered merge restores everything from remote) | **FAIL** (DATA-QA-003) |
| Account deletion must affect the intended data scopes only, without orphaning either side | `services/auth.ts: deleteAccount` (Firestore delete → Auth delete → guest mode) | E2 — ordering is correct (avoids orphaned Firestore docs), but a failure *between* the two steps (e.g. `auth/requires-recent-login`, explicitly handled elsewhere in the UI) leaves a live Auth account with already-wiped Firestore data | PARTIAL (DATA-QA-004) |
| One device's stale state should not blindly overwrite newer legitimate state without the merge policy accounting for it | `mergeAndSyncUserData` — MAX/UNION fields (xp, streak, solved, rewarded, badges, learningProgress) correctly resist stale overwrite; the fields in DATA-QA-002 do not | PARTIAL (split PASS/FAIL by field, see Merge Matrix) |
